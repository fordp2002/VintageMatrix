All PCB reads and writes go through KiCad's Python API ([14-kicad](14-kicad.md)), never by editing the board file directly.

## Placement

- **PCB-001** [Decided] Switch footprints are placed at each key's stem centre (KEY-001), converted to mm only when sent to KiCad (DIM-010, DIM-011).
- **PCB-002** [Decided] Per-key modules are placed relative to the stem centre (KEY-002).
- **PCB-003** [Decided] Connectivity of managed elements comes from the matrix (MAT-001). The PCB generator does not infer connectivity, and no netlist file is involved (PCB-016).
- **PCB-004** [Open, deferred] Automatic placement of parts other than switches, diodes, and canvas-placed controllers (e.g. connectors). Routing is decided: optional Freerouting (PCB-029). See [Q09](../decisions/Q09-autoplacement-routing.md).
- **PCB-006** [Decided] The board outline comes from `outline` (KEY-007) and is generated by VintageMatrix like any other managed element. Changing the outline in the design, even after routing, updates it on the board at the next generation.
- **PCB-041** [Decided] The outline is **locked** in KiCad, to show the user it must not be edited there. Changes belong in the design. Like any managed element, a changed outline is restored on update (PCB-010).
- ~~**PCB-042** The outline is delivered inside a tagged footprint.~~ [Removed in 0.5]: the outline is recognised as ours by PCB-044 instead.
- **PCB-044** [Proposed] The outline is drawn directly on the board-edge layer (a rectangle, or the imported segments). **VintageMatrix owns the board-edge layer**: everything on it is treated as the outline and is managed by the generator. The board shape is defined only in the design, so cut-outs and other edge shapes belong in the design too, not in KiCad.
- **PCB-043** [Proposed] Changing the outline rips up no tracks. Tracks that end up outside or too close to the new edge are reported by KiCad's DRC as usual.
- **PCB-019** [Decided] The PCB never requires a controller, and a `controller` section never requires the controller to be on the PCB (FW-012, PRIN-009). With a module off-board or no controller at all, the matrix nets join the user's schematic, e.g. at a connector, by name as usual (PCB-016).

## Controllers on the PCB

- **PCB-020** [Decided] A controller placed on the canvas (GUI-014) is placed on the board by the generator as a tagged element (PCB-007), with tag `controller:<id>/<role>`, and is reconciled like any other (PCB-009). Its footprint comes from the module definition (FW-014) or, for a discrete MCU, from the controller section.
- **PCB-021** [Proposed] A controller is on the canvas when the `controller` section has a `position`. It may also have a `rotation` (KEY-003).
- **PCB-026** [Decided] **Everything is placed by its footprint origin.** A position in the design is where the KiCad footprint's origin goes. For switches, the origin is the stem centre (KEY-009).
- **PCB-022** [Decided] **The generator only connects pins it knows about.** Today that is every pad of its own switches and diodes, and the matrix row/column pins of a controller (MAT-006, FW-015). It assigns no net to any other pin. More pin types may be supported in future ([Q17](../decisions/Q17-connecting-other-pins.md)).
- **PCB-023** [Decided] On a tagged controller, the generator owns the footprint, position, orientation, and the nets of the pins it knows about. Nets on its other pads are **not** reverted (an exception to PCB-010); their handling is [Q17](../decisions/Q17-connecting-other-pins.md).

## Diodes

- **PCB-034** [Decided] The generator **places and connects** every diode the design's scheme requires (MAT-005), as tagged elements: `key:<id>/diode`, `row:<id>/diode`, or `col:<id>/diode`.
- **PCB-035** [Decided] **Key diodes:** each key's switch and diode are wired in series between the key's row net and column net, with the diode oriented by `direction` (MAT-015).
- **PCB-036** [Proposed] **Pad conventions**, insisted on as for KEY-009: switch footprints have pads `1` and `2`; diode footprints have pad `1` = cathode and pad `2` = anode, as in KiCad's standard libraries. Footprints that don't follow these conventions are not supported.
- **PCB-037** [Proposed] The net between a key's switch and its diode is named `VM_K_<key id>`.
- **PCB-038** [Decided] **Row/column diodes:** one diode per row (or column) line, in series between the matrix line and the controller pin or connector side, oriented by `direction`.
- **PCB-039** [Proposed] With row/column diodes, the controller/connector side keeps the shared net name (MAT-011), so the contract with the user's schematic is unchanged. The matrix side is named `VM_<name>`.
- **PCB-040** [Proposed] Row/column diodes are placed by the user on the canvas (GUI-017), and their position is stored on the row/column object. A row/column diode with no position is reported as a warning and is not placed.

## Completeness

- **PCB-024** [Decided] Keys, a controller, and the matrix rows/columns are sometimes enough for a complete design (e.g. a module that carries its own USB connector), but often they are not. Everything else comes from the user, e.g. through their schematic joined by net name (PCB-016). VintageMatrix never claims a board is complete.
- **PCB-025** [Proposed] After an update the generator reports, as information, which pins of a placed controller it left unconnected, so the user can see what remains to be done.

## Ownership: tagged elements

The board file is shared: it holds both elements VintageMatrix manages and the user's own work.

- **PCB-007** [Decided] Every footprint the generator adds carries a custom **VintageMatrix field** holding a reference to the design object it comes from. The tag is simply how the generator recognises its own footprints for PCB-005.
- **PCB-005** [Decided] **The generator only edits things that are its own.** It never adds to, modifies, or removes anything else on the board. Its own things are its tagged footprints (PCB-007) and the board outline (PCB-044).
- **PCB-008** [Proposed] The field is named `VintageMatrix` and hidden on all layers. Its value is `<kind>:<id>/<role>`, built from stable design IDs (CON-010), e.g. `key:k_a/switch`, `key:k_a/diode`, `key:k_a/stab`. Each value is unique on the board.
- **PCB-011** [Decided] The generator creates only its own things (PCB-005). Apart from managing them, its only action on the board is ripping up tracks connected to its parts (PCB-027, PCB-028). The board outline is the one generated thing recognised by something other than a tag (PCB-044) ([Q15](../decisions/Q15-tagging-untaggable-pcb-items.md)).

## Updating the PCB

- **PCB-009** [Decided] An update **reconciles** the board with the design:
  - an element the design requires but the board lacks is **added**, even if the user deleted it (e.g. a deleted key's switch reappears);
  - a tagged element whose design object no longer exists is **removed**;
  - a tagged element that differs from what the design requires is **updated**.
- **PCB-010** [Decided] Changes the user makes in KiCad to tagged elements (e.g. moving a switch) are overwritten on the next update. To change a managed element, the user changes the design, through the UI or by editing the design file. These are the same thing, since the UI edits the design file through the API (GUI-001). Every restore is reported so the user can see what was reverted.
- **PCB-027** [Decided] **The user's tracks are removed only when a part has to move.** When an update moves a tagged footprint (because the design changed, or to revert a user move, PCB-010), the tracks connected to it are ripped up using KiCad's own API call for this. No other routing is touched.
- **PCB-028** [Decided] When something other than position changes (e.g. a pad's net), only the connections affected are ripped up.
- **PCB-045** [Decided] Every footprint the generator places is **locked** in KiCad, like the outline (PCB-041), to show the user it is managed from the design.
- **PCB-012** [Decided] The board file is user-owned: it lives in the user's KiCad project, is versioned by the user, and is not a disposable artifact. Disposability (PROV-001) applies to the tagged elements, not the file (PROV-008).
- **PCB-013** [Proposed] An update is a single API operation (`generate pcb`). It reports every added, updated, removed, and restored element, and every ripped-up connection, as diagnostics (CON-013), keyed by the tag value.
- **PCB-014** [Proposed] Two tagged elements with the same tag value is a **warning** (e.g. the user duplicated a switch). The generator keeps one, reconciles it, and removes the duplicate.

## Joining the user's schematic (interim, per Q14)

Until schematic generation exists (KICAD-006), the matrix lives only on the board and joins the user's schematic by net name.

- **PCB-015** [Decided] Matrix footprints the generator places are marked **Not in schematic** in KiCad, so *Update PCB from Schematic* leaves them alone.
- **PCB-016** [Decided] The generator connects each managed pad by assigning it to a net **by name**, using the row/column names from the matrix (MAT-011). It never produces or imports a netlist file.
- **PCB-017** [Proposed] Before updating, the generator checks that every row/column net name exists on the board, i.e. the user's schematic provides it and has been synced. A missing net is a **warning** naming the row/column and the expected net name. The pads are still assigned, so the board shows the gap.
- **PCB-018** [Decided] When schematic generation arrives, PCB-015 to PCB-017 are replaced by syncing from the generated schematic. The design file is unaffected.

## Autorouting (optional)

- **PCB-029** [Decided] The PCB can be routed automatically by calling **Freerouting** ([freerouting.app](https://www.freerouting.app/)). Autorouting is **optional**: everything else in VintageMatrix works without it. If Freerouting is unreachable, the route operation fails with a clear diagnostic and changes nothing (ARCH-006).
- **PCB-030** [Proposed] Autorouting runs only when the user (or a script) explicitly asks for it (`route`, API-008). It never runs as part of `generate pcb`.
- **PCB-031** [Proposed] The board goes to Freerouting as a Specctra DSN file exported by KiCad, and the result comes back as a Specctra SES file imported by KiCad, both through the KiCad API (KICAD-001, KICAD-010). VintageMatrix passes these files along and never writes them itself.
- **PCB-032** [Proposed] Autorouted tracks are treated as **the user's tracks**: they are not tagged or reconciled, and are ripped up only under PCB-027 and PCB-028. This keeps tracks out of [Q15](../decisions/Q15-tagging-untaggable-pcb-items.md).
- **PCB-033** [Proposed] Using the public service uploads the board to a third party, so it needs the user's explicit consent. The Freerouting endpoint is configurable, so a self-hosted Freerouting can be used instead.

## Extension points

**Add a switch footprint mapping.** Map a `switch` value (KEY-005) to a KiCad footprint library reference. Reference footprints from upstream or standard KiCad libraries; do not copy footprint files in (UP-001). The footprint's origin must be the stem centre (KEY-009).

**Add a managed element type** (e.g. a per-key LED). Give it a `<role>` for PCB-008 and make sure it can carry the VintageMatrix field (PCB-011). It is then reconciled by PCB-009 like any other tagged element.
